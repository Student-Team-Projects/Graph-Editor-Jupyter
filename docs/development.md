# Development guide

How to set up the project and work on it.

## Layout of the repo

```
src/graph_editor_jupyter/   Python package
  __init__.py               edit(graph): shows the widget
  widget.py                 GraphWidget: syncs graph data with the browser, applies edits (anywidget)
  layout.py                 first layout: planarity check, crossing count
  static/                   compiled front end (generated by npm, not in git)
js/                         TypeScript front end
  src/widget.ts             draws the graph, dragging, force/freeze (d3-force), editing
  src/widget.css            styles
tests/                      pytest tests
docs/                       requirements, research, policies
main.ipynb                  demo notebook
```

Python sends the graph to the browser as lists in `GraphWidget` traits (`nodes`, `edges`, `positions`, `width`, `height`). The TypeScript code reads them with `model.get(...)` and redraws when they change. Positions are normalized to [0, 1].

## One-time setup

You need **Python 3.10+** and **Node.js 18+**.

```
python -m venv .venv
# activate it (Windows: .venv\Scripts\activate, Linux/macOS: source .venv/bin/activate)
pip install -e ".[dev]"

cd js
npm install
npm run build
```

`pip install -e` makes Python use the source code directly, so Python changes apply after restarting the notebook kernel.

## Everyday commands

| What | Command |
|---|---|
| Rebuild the front end | `cd js && npm run build` |
| Rebuild automatically on save | `cd js && npm run dev` |
| Type-check TypeScript | `cd js && npm run typecheck` |
| Run TypeScript tests | `cd js && npm test` |
| Run Python tests | `pytest` |
| Start Jupyter | `jupyter lab`, then open `main.ipynb` |

After rebuilding the front end, rerun the notebook cell. Restart the kernel after changing Python code.

**Hot reload (optional):** start Jupyter with the environment variable `ANYWIDGET_HMR=1` while `npm run dev` is running. The widget then updates in the notebook as you save TypeScript files.

## Testing policy

- **Every new feature or bug fix comes with tests** in `tests/`, in the same pull request.
- A bug fix starts with a test that fails because of the bug, then the fix makes it pass. This applies to every mistake found, including ones found during review: each gets a regression test.
- TypeScript logic without the DOM (physics, sizes) lives in separate modules like `js/src/forces.ts` and is tested with `npm test` (Node's built-in test runner). Code that needs a browser (mouse handling, drawing) is checked by hand for now.
- Run `pytest` (and `npm run typecheck` and `npm test` for TypeScript changes) before every commit. Don't merge with failing tests.
- Test logic in Python (layout, planarity, crossings, graph sync), where it is easy. UI behaviour in the browser is checked by hand in `main.ipynb`. Describe what you checked in the pull request.

## Status

Done: package skeleton, widget draws the graph, correct planarity check, crossing-free first layout for planar graphs with vertices spread apart (with tests).

**How the first layout is chosen** (`layout.py`): each connected component gets several candidate layouts (tidy tree layout for trees, Tutte embedding for 3-connected planar graphs, Kamada-Kawai, spring layout with several seeds, NetworkX planar layout). The one with the fewest crossings wins, ties broken by the most space between vertices. If the winner is crossing-free but cramped, a force step spreads it out, rejecting any move that would add a crossing.

**Non-planar graphs** (`_CrossingSearch`): two phases. First the fewest crossings (vertex movement with random shakes, from the best candidates including a planarization candidate), then better looks (stress plus a vertex-edge distance term) without adding crossings. Details, sources and results: [research/04-crossing-minimization.md](research/04-crossing-minimization.md).

Done: dragging, force/freeze toggle (d3-force, starts frozen so the first layout stays as computed; force mode is gentle, see research/03), adding and removing vertices and edges, edits go straight into the NetworkX graph.

Not done yet: labels (showing, editing, colors), see requirements.md.

**How edits travel:** the browser sends a message (`add_node`, `add_edge`, `remove_node`, `remove_edge`) to `GraphWidget._on_msg`, which changes the NetworkX graph and updates the `nodes`/`edges` traits. Positions are owned by the browser and sent back in the `positions` trait after a drag or when the physics settles.
